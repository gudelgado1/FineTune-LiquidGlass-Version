# Apple HIG and API evidence for the EQ preset background

Research date: 2026-11-01. Scope: official Apple HIG, AppKit and SwiftUI documentation. The reported scenario is a change in the main FineTune panel's translucency and control colors when the preset chooser takes focus. This note supplies design/API constraints; it does not independently establish the runtime cause or certify a fix. No product code, UI or system settings were changed by this research.

## Design guidance

| Area | What Apple recommends | Implication for FineTune |
| --- | --- | --- |
| Material hierarchy | Liquid Glass primarily separates controls/navigation from content. Standard materials structure content; custom glass should be selective. `regular` is appropriate for text-rich surfaces including popovers, while `clear` targets visually rich media backgrounds. Choose materials semantically, not by a sampled shade. [HIG: Materials](https://developer.apple.com/design/human-interface-guidelines/materials) | A regular-glass transient panel is not inherently forbidden. A standard semantic content backing is also a reasonable design choice. HIG alone cannot prove that replacing the main panel's glass is the correct bug fix. |
| Presentation | Keep transient popovers focused, avoid cascaded popovers, preserve work on automatic dismissal, and animate content-size changes smoothly. [HIG: Popovers](https://developer.apple.com/design/human-interface-guidelines/popovers) | Prefer a native menu or an inline choice when a chooser would otherwise create a hierarchy of popovers. FineTune's parent is a custom panel, so the recommendation must not be presented as an `NSPopover` API restriction on that panel. Test first-click opening, selection, cancellation, outside-click dismissal and returning focus. |
| Appearance | Respect the system appearance; validate light/dark legibility, including Increase Contrast and Reduce Transparency separately and together. Use adaptive semantic colors. [HIG: Dark Mode](https://developer.apple.com/design/human-interface-guidelines/dark-mode) | Existing app appearance overrides should propagate consistently to parent and chooser. Do not compensate for inactive colors with hard-coded white/black fills that fail another appearance. |
| Motion | System components already supply feedback; custom frequent interactions should avoid gratuitous motion and should remain interruptible. [HIG: Motion](https://developer.apple.com/design/human-interface-guidelines/motion) | A preset change should not need a decorative whole-panel fade or material replacement. Test size transitions and rapid repeated selections; honor Reduce Motion. |

## Implementation facts, distinct from HIG

- SwiftUI `appearsActive` is a readable/writable environment value. On macOS, key-window content normally appears active; some contexts, such as a main-window toolbar, can remain active without key status. Inactive appearance can desaturate accent colors, dim some content and make selections gray. Therefore gray controls alone do **not** establish that EQ processing became disabled. [EnvironmentValues.appearsActive](https://developer.apple.com/documentation/swiftui/environmentvalues/appearsactive)
- `controlActiveState` is deprecated in the current documentation in favor of `appearsActive`. Since macOS 15, `.key`/`.active` map to `appearsActive = true`, and `.inactive` maps to `false`. This documents control appearance, not a promise that overriding the environment fixes the native glass compositor's blur. [EnvironmentValues.controlActiveState](https://developer.apple.com/documentation/swiftui/environmentvalues/controlactivestate)
- `NSVisualEffectView.state` defaults to `.followsWindowActiveState`; that state makes the backdrop follow window activation. `.active` requests an always-active backdrop. This describes `NSVisualEffectView`, and must not be automatically attributed to SwiftUI's `.glassEffect` implementation. [state](https://developer.apple.com/documentation/appkit/nsvisualeffectview/state-swift.property), [followsWindowActiveState](https://developer.apple.com/documentation/appkit/nsvisualeffectview/state-swift.enum/followswindowactivestate), [active](https://developer.apple.com/documentation/appkit/nsvisualeffectview/state-swift.enum/active)
- Behind-window blending samples desktop/other windows; within-window blending samples the same window only. Within-window effect views must not overlap; behind-window overlap is allowed and the lower view wins. These are different composition contracts, not interchangeable blur-strength knobs. [behindWindow](https://developer.apple.com/documentation/appkit/nsvisualeffectview/blendingmode-swift.enum/behindwindow), [withinWindow](https://developer.apple.com/documentation/appkit/nsvisualeffectview/blendingmode-swift.enum/withinwindow)
- AppKit already supplies visual-effect backgrounds for native popovers. A custom panel may need its own backing, but stacking an additional effect over an existing native backing requires justification. [NSVisualEffectView overview](https://developer.apple.com/documentation/appkit/nsvisualeffectview)
- For an AppKit glass wrapper, only `NSGlassEffectView.contentView` is guaranteed to sit inside the glass. Arbitrary subviews have no guaranteed ordering relative to the glass/content. [NSGlassEffectView.contentView](https://developer.apple.com/documentation/appkit/nsglasseffectview/contentview)

## Recommended verification, not a confirmed implementation

First distinguish logical EQ state, focus/active appearance and optical material composition. Record parent/child key status and material ownership at chooser opening, selection and dismissal. Isolate one variable per comparison: session-scoped active appearance, backing ownership, then any semantic material substitution. A scoped active-appearance override is an experiment, not a reason to force every app window permanently active.

Check the composed parent and chooser over both simple light/dark surfaces and detailed backgrounds, in both appearances. Repeat with Reduce Transparency, Increase Contrast and Reduce Motion; system Liquid Glass adjusts for these settings. [Apple: Meet Liquid Glass](https://developer.apple.com/videos/play/wwdc2025/219/)

Acceptance should cover legible foregrounds, no unintended exposure of detailed content behind the panel, stable backing ownership, correct focus restoration, and no unexplained material replacement during selection. Legitimate system inactive styling should be distinguished from the reported defect. Neither HIG nor the cited APIs specifies a fixed blur radius, tint alpha or exact shader response when a child window becomes key. Pixel-identical or constant-blur claims require runtime evidence beyond these sources.

## Local reproduction and chosen fix

The user's Preview 9 recording (2026-11-01 14:23:38) shows stronger parent-panel blur as the preset chooser becomes key. A standalone laboratory reused `FluidMenuBarExtraWindow`, `RootViewModifier`, `PopoverHost`, `GlassBackgroundModifier`, and then the actual `EQPresetPicker`, over an owned light/dark text backdrop; no audio services were started. Captures included only the laboratory's owned backdrop and probe, with child-window inclusion explicitly disabled, excluding other applications and the desktop.

Three comparisons separated the cause from a visual workaround:

- The existing custom chooser takes key focus: the parent's appearance becomes inactive and scene phase becomes background. In a foreground-free 140×30-pixel region, mean absolute grayscale difference was 10.1652/255 when opening it.
- Setting `appearsActive = true` kept controls colored but produced the same background difference. This was rejected as an incomplete fix.
- Native menu tracking kept the parent appearance and scene active. The same measured patch was identical before/after opening the native prototype. The main panel glass was retained; no shader, opacity, tint, or private glass API was modified.

The EQ preset selector now uses a native `Menu` containing an inline selection `Picker`. Categories and selected-item checks remain native, and saved presets keep selection plus a separate `Delete User Preset` submenu, so an unselected preset can be deleted without applying its curve first. Rename remains in the existing EQ panel. Explicit action dismissal uses Apple's documented [enabled behavior](https://developer.apple.com/documentation/swiftui/menuactiondismissbehavior/enabled).

The actual selector was exercised with built-in categories, a disposable in-memory saved preset, its deletion, and keyboard selection/cancellation. Parent active appearance was preserved in light and dark laboratory appearances. This is bounded compositor evidence, not an assertion that all pixels, accessibility settings or macOS versions were certified. Physical validation in the next preview is still required. Other searchable/editor popovers retain their focus behavior; this fix is scoped to EQ preset selection.

With the actual selector, both light and dark captures had zero mean/max pixel change in the measured patch on menu opening. This does not imply the entire panel is pixel-identical. Explicit menu dismissal closed a mouse selection immediately in CUA. Arrow navigation highlighted the expected item; Return followed by Escape produced the selected value in the automation harness. Physical Return-only dismissal remains a retest item rather than a certified keyboard result.

Latest local validation after the selector change: isolated run `20261101-144211-222775`, 1020 passed, zero failures/skipped; optimized arm64 Release built. No audio-engine or HUD material change was made for this visual correction.
